# Agent build spec

Implements [the agent PRD](AGENT-PRD.md). This is one on-demand agent, hosted by either desktop app, with durable local work records. Existing reviewer code, tests, input pack, portable review instructions and historical results stay intact.

## Delivery

`agent/` is the ready-to-open product folder. Its `AGENTS.md` is the shared agent definition; `CLAUDE.md` imports that definition for Claude Code. `START HERE.md` gives the lead the opening words. The shared definition loads the operation reference only when working with records, and the support review policy when assessing a release.

The source folder and ZIP contain no company state. Default private state lives outside the replaceable product folder, in the user's Application Support directory under Support Release Readiness. Requests, inbox and views live inside that workspace. Each company uses a separate workspace. Both hosts need permission for the chosen directory; the agent explains the host's normal file/helper approval and never changes global permissions. The desktop acceptance test records actual prompts, targeting one remembered helper approval and one workspace grant. No account service, server, API key, third-party package or additional interpreter is required. First supported OS: macOS, using `/usr/bin/osascript -l JavaScript` and Foundation. Desktop usability and work-device permission checks remain separate release gates.

To update, close the old session, replace only the downloaded product folder, open it and select the same company workspace. Keep active records in local Application Support, not iCloud/Dropbox/shared sync folders. Share generated outputs; an active workspace is single-writer. Handoff to another computer requires copying the complete closed workspace and checking its integrity, not concurrent sync.

The existing Python runner stays a developer experiment. Product model calls run in the user's current host session, not a nested `codex exec` process. Python may build/test a ZIP on the developer machine; it is absent from the user path.

## Persistent records

One authoritative sequence of numbered JSON records stores complete state, the previous record's SHA-256 and a dated event. SHA-256 is implemented in plain JavaScript and tested against standard ASCII and UTF-8 vectors and Python's reference. The helper validates the chain before reads or writes. Records have a fixed schema version and workspace identity. A mutation supplies the expected revision; a native exclusive lock and atomic rename prevent conflicting writes. A failed mutation cannot change the accepted head. The lock records a process ID and unique token. Recovery checks the owner is dead and requires the exact token and explicit confirmation; no age-only automatic unlock may evict an active writer.

Company profile drafts persist while onboarding. Confirmed profile includes people, support model, timezone, notice rule and decision roles. Onboarding distinguishes elapsed hours, local calendar days and business days. Business days require an explicitly supplied holiday list and confirmed calendar. Each release owns its source versions, facts, actions, reviews and reported human decisions. Release IDs and action IDs remain stable. Supported action states: open, in progress, reported complete, complete and needs review.

Each imported text source has an ID, version, authority (draft, approved or observed), attribution, content hash and optional scoped facts backed by source passages. The helper reads original text files directly from the workspace inbox; it rejects symlinks, path traversal, unsupported extensions and files over the size limit. Pasted text and host-extracted attachments use attributed content intake. Original text is preserved in immutable content blobs. Quote resolution first matches exactly, then allows NFC, whitespace and curly-quote normalization to select an original paragraph. A citation can select a saved fact instead of repeating its quote; the helper inserts the actual stored passage. Stored citations use that original passage; word substitutions still fail. A draft does not replace an approved current source. User/colleague statements remain attestations. Invalid references and quotes are rejected. Unsupported file types are read through host capabilities if available, then preserved as an attributed text extract; otherwise the agent requests an extract without inventing content.

An action depends on named facts in named sources, rather than an entire product document's timestamp. Updating a source compares those scoped fact values. Only changes affecting a dependency reopen the action; its ID, earlier completion and reason remain in history. New conflicting evidence does not establish a new approved product decision automatically. The model interprets sources; helper checks establish storage, quote existence and stated dependencies, not semantic truth.

An assertion can set reported complete. Complete requires cited current non-draft evidence, an explicit accepting person and an evidence revision consistent with dependencies. Named human decisions are recorded as reported decisions with evidence; the helper never executes them or treats the agent as an approver. The lead receives unknowns and proposed next work when evidence is insufficient.

## Operations

A small system-JavaScript helper supports status, inspect, profile, release, source, action, review, decision, export, rebuild and calculate. The host writes a request file inside the workspace and invokes the helper through its existing command tool. The user does neither. All writes validate input shape and revision; file IDs cannot contain paths. Source text is stored by the helper, not executed. No outbound network operation exists.

Status reads accepted state and shows current work. Inspect selects one release, its current sources and latest review, excluding other releases and historical source content unless explicitly requested. The full history remains saved and can be requested. Existing action updates may supply only changed fields; the merged action must still pass every completion and dependency rule. Review requires valid citations and an allowed phase recommendation. It records unresolved findings, resolved observations, unknowns, selected source identities and proposed actions. Ready recommendations reject unresolved serious findings. Changed dependencies prevent a current-ready recommendation until reconciled. A review's valid schema does not certify its meaning.

At rollout, the agent reads signals and matching customer reports first. A supplied pause condition prompts an immediate recommendation and a short saved review before it reconciles earlier preparation. This keeps an urgent alert from waiting behind administrative closure. It still requires the named person's authorization and execution evidence. A follow-up record that establishes an unnamed group's individual resolution does not create a new requirement for separate case IDs; unresolved named cases remain tracked.

Calculate validates explicit offset timestamps, nonnegative finite numbers, exposure, equal windows and category totals. It returns a deadline under the confirmed notice rule, handling-load arithmetic or exact rate comparisons with input provenance. Hours use elapsed time; calendar/business days use the supplied IANA timezone and Foundation calendar arithmetic, with explicit holidays for business days. Return both rate increase and contact-count increase with units. Bad/missing numbers or an unknown business calendar return failure, not an invented value.

Markdown tracker/history views and Markdown/CSV shared exports are derived from accepted records. A record commit precedes view generation. View hashes detect manual edits; preserve edits in inbox and stop before overwriting until an explicit rebuild. The agent reads preserved edits as attributed reply material. Interrupted/missing views are rebuilt from intact history. Corrupt authoritative records are preserved and block writes; recovery is not an automatic silent rollback. Exports use explicit fields and no source text or customer details by default; requested sensitive excerpts need a deliberate selection. Shared files are dated and note reported versus accepted completion and pending human authority. The agent can read a pasted colleague reply into an attributed source and update the relevant action.

## Testing and release gates

Automated tests run native helper operations against temporary workspaces, including concurrency and interrupted writes. Compare SHA-256/date/rate outputs with independent Python standard-library values on the developer machine. Packaging tests inspect the ZIP, ignored state and unchanged README. Keep all existing software checks passing.

Behavioral checks use fresh Codex/Claude sessions in isolated copies of the downloadable product with synthetic evidence only, no evaluator key, no production connectors and no browser automation. Record model, host version, prompt, artifacts, tool events, expected outcome, observed outcome and failures. CLI-hosted checks exercise behavior, not desktop clicks or a nontechnical person's usability. The requested Opus 5.5 review evaluates the PRD before build and the implementation after changes; review findings are resolved through checks.

Do not declare production readiness until A01–A19 have their applicable evidence, including actual supported desktop setup and independent support-lead use. Missing access is recorded as not run, not a pass. Publish development changes through a pull request; the existing root README remains byte-for-byte unchanged.
